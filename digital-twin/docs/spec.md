# 디지털 트윈 기능명세

디지털 트윈을 다른 구획보다 먼저 개발한다. 이 문서는 무엇을 만들고, 어느 수준이면 끝난 것인지를 정한다. 어떻게 검증하는지는 [harness.md](harness.md)에 있다.

## 1. 목표

브라우저에서 사이트를 열면 용접 현장이 3D로 보이고, 로봇이 `robot/state`를 따라 움직이며, 작업판 위에 용접 경로와 작업 상태·알람이 표시된다. 서버·브로커·실제 로봇 없이 녹화된 시나리오(픽스처)만으로 이 전부가 동작해야 한다.

트윈이 먼저 끝나야 하는 이유: 사이드 패널과 서버는 "어느 셀의 어느 로봇"을 가리킬 대상이 있어야 붙일 수 있다. 트윈이 그 대상과 이름 규칙(prim 경로 = 토픽 = 설정 키)을 확정한다.

## 2. 품질 기준

참조는 [realvirtual WEB](https://github.com/game4automation/realvirtual-WEB)의 공개 데모 화면이다. "그 수준"을 아래 항목으로 풀어서 기준으로 삼는다.

| 요소 | 기준 | 수단 |
| --- | --- | --- |
| 환경광 | 실내 창고형 환경으로 금속 면에 반사가 보인다 | three `RoomEnvironment`(절차적, 외부 파일 없음)을 PMREM으로 굽는다 |
| 키 라이트 | 방향광 1개. 로봇·지그가 바닥과 작업판에 그림자를 떨어뜨린다 | 그림자 맵 2048, PCF + radius로 부드러운 경계(three 0.187에 PCFSoft 없음) |
| 접촉 음영 | 물체가 바닥에 붙어 보인다(떠 보이지 않는다) | SSAO(N8AO) |
| 색 관리 | 흰색이 날아가지 않고 어두운 곳이 뭉개지지 않는다. 안전색(주황·노랑)이 바래지 않는다 | Khronos PBR Neutral 톤매핑, sRGB 출력, 노출 고정(M3에서 AgX를 써 보니 색이 바래 바꿨다) |
| 계단 현상 | 펜스·케이블 같은 가는 형상이 깜빡이지 않는다 | MSAA 4x |
| 재질 | 전부 PBR. 도장 강판, 무도장 강재, 고무, 콘크리트, 안전 노랑 등 공용 재질 8~12종 | 재질 라이브러리를 에셋이 공유 |
| 형상 | 모서리에 베벨이 있다. 로봇은 제조사 CAD 메시 기반이다. 박스 그대로인 에셋이 없다 | Blender 모델링 기준(`assets.md`) |
| 선택 표시 | 선택한 로봇·마커에 외곽선이 보인다 | postprocessing Outline |
| 배경 | 중립 톤 배경. 바닥은 사이트 경계 밖에서 자연스럽게 사라진다 | 그라데이션 + 안개 |

알아둘 점 세 가지.

- realvirtual WEB은 three.js를 직접 쓰고, 우리는 R3F를 쓴다. 엔진이 같으므로 같은 화면을 낼 수 있다.
- realvirtual WEB은 AGPL-3.0이다. 코드를 복사하지 않고 화면 품질만 참고한다.
- 그 화면의 품질은 렌더링 설정보다 에셋에서 나온다. 렌더링 설정은 며칠이면 끝나고, 나머지 시간은 모델링에 든다.

| --- | --- | --- | --- | --- | --- |

## 3. 범위

만든다: 정적 배경, 로봇 관절 추종, 용접선, 작업 상태·진행률·알람·연결 상태 표시, 카메라 조작과 프리셋, 선택, 사이트 전환.

만들지 않는다: 물리·충돌 시뮬레이션, 역기구학(관절각은 서버가 준다), 3D 안에서의 경로 편집(수정은 사이드 패널의 영상 위에서 한다), 레이아웃 편집, VR/AR, PLC 연결.

### 구획 경계

| 무엇 | 어디 |
| --- | --- |
| USD 에셋, 사이트 조립, 빌드, site-config, 픽스처, 하네스 | `digital-twin/` |
| 씬을 그리는 코드 | `frontend/src/scene/` |
| 트윈만 띄우는 개발용 화면(트윈 랩) | `frontend/src/lab/` |
| site-config와 메시지의 스키마 | `contracts/schemas/` |

씬 코드는 store만 읽는다. 트윈 우선 개발 동안은 MQTT `bus` 대신 픽스처 재생기가 store를 채운다. 나중에 `bus`로 바꿔도 씬 코드는 바뀌지 않는다.

씬의 입출력은 이것이 전부다.

- 입력: site-config 1개, store의 셀별 상태(관절각, 작업 상태, 경로, 진행률, 알람, 연결 상태)
- 출력: 선택 이벤트(`{site, cell, kind, id}`)

## 4. 기능 목록

우선순위: P0은 M1~M2에서 반드시, P1은 M2~M4, P2는 여유가 있을 때.
검증 열은 하네스 단계다(L0 정적 검사, L1 에셋 검사, L2 단위 테스트, L3 씬 상태 테스트, L4 스크린샷 비교, L5 성능 측정, H 사람 검수).

### 에셋 (AS)

| ID | 기능 | 순위 | 완료 기준 | 검증 |
| --- | --- | --- | --- | --- |
| AS-01 | 임시 에셋: 박스 수준의 로봇 자리·작업판·바닥 | P0 | 조선소 사이트가 파이프라인을 끝까지 통과한다 | L1 |
| AS-02 | 로봇: 6축 용접 로봇 + 토치, URDF + 링크별 메시 | P0 | 모든 링크 메시가 로딩된다. 관절 이름이 `robot/state`의 이름과 같다 | L1, L3 |
| AS-03 | 작업판: 크기(mm)를 인자로 받고 원점 모서리에 표식이 있다 | P0 | site-config의 판 크기와 씬의 판 크기가 같다 | L3 |
| AS-04 | 재질 라이브러리 | P0 | 에셋이 자체 재질을 갖지 않고 라이브러리를 참조한다 | L1 |
| AS-05 | 지그·포지셔너 | P1 | 작업판을 받치는 형상이 있다 | H |
| AS-06 | 조선소 배경: 블록 일부, 정반, 크레인 레일, 용접기, 케이블, 펜스 | P1 | 품질 기준 표를 만족한다 | L4, H |
| AS-07 | 공장 배경: 용접 셀(펜스, 흄 후드, 용접 테이블), 바닥 마킹 | P1 | 품질 기준 표를 만족한다 | L4, H |
| AS-08 | 현장 카메라 모형(카메라 위치 표시) | P2 | 셀마다 카메라 위치에 보인다 | H |

## 5. 트윈이 구독하는 토픽

트윈 우선 개발에 필요한 스키마만 M0에서 `contracts/schemas/`에 먼저 만든다. 필드 이름은 거기서 확정한다.

| 토픽 | 트윈이 쓰는 내용 | 쓰는 기능 |
| --- | --- | --- |
| `robot/state` | 관절 이름별 각도(deg), `ts` | DY-01, DY-09 |
| `task/state` | 상태 이름, `task_id` | DY-04 |
| `task/proposal` | 경로 점 배열(판 좌표 mm) | DY-03 |
| `task/snap` | 수렴된 경로 점 배열 | DY-07 |
| `task/progress` | 진행률(0~1) | DY-06 |
| `alarm` | id, 심각도, 발생·해제 | DY-05 |
| `status` | online / offline | DY-08 |

`vision/metrics`, `cmd/*`, `heartbeat`는 트윈이 다루지 않는다.

| M2 | 동적 층 완성: 상태, 알람, 진행률, 선택, 프리셋 | P0 전부와 DY·IX의 P1이 L3까지 통과 |
| M3 | 품질 올리기: 조명·그림자·SSAO·재질, 로봇과 조선소 에셋 | 기준 스크린샷을 사람이 승인. 성능 예산 통과 |
| M4 | 공장 사이트 추가 | `frontend/` 코드 변경 0줄로 두 번째 사이트가 뜬다 |
| M5 | 프론트 통합: 픽스처 재생기를 MQTT `bus`로 교체, 태블릿 확인 | 같은 픽스처를 브로커로 재생해도 L3이 통과한다 |

M3을 M2 뒤에 두는 이유: 구조가 맞는지 박스로 먼저 확인해야 에셋을 다시 만드는 일이 없다.
